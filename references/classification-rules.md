# 分类体系与判定口径

## 半通用：体系可以变

分类体系**不是写死的**。每次运行都实时读一次实际的收藏夹清单（`collect.py` 输出的 `snapshot.json`）：

- 目录里已有的夹 → 直接用；
- 计划里出现、目录里没有的夹 → 阶段 5 时新建；
- 目录里有、计划里没用到的夹 → 不动。

所以用户随时可以加夹、改名、删夹，不需要改本 skill。下面这套只是**默认参考配置**，也是判定时的候选集合。

## 默认分类体系

14 个去向（13 个主题夹 + 1 个兜底夹）：

| 夹 | 内容 |
|---|---|
| 计算机 | 编程语言系统课、计算机系统/网络/性能、自学路线、数据结构与算法 |
| 游戏开发 | **只看开发技术与游戏设计**：引擎与工具、程序、技术美术、策划、图形渲染、UI/交互、对话系统、架构、独立开发 |
| 游戏相关 | **游戏的非开发内容**：游戏评论/评分、行业观察与求职、发行运营、游戏文化/发展史、杂谈盘点、社群梗 |
| AI | AI 编程工具与工作流、Agent/RAG、AI 美术、本地模型部署 |
| 摄影 | 拍摄、后期、器材 |
| 篮球 | 技术教学、战术分析、集锦 |
| 健身康复 | 训练计划、解剖、康复 |
| 音乐 | 乐理、乐器、制作 |
| 数学 | 线代、微积分、概率统计、离散 |
| 生活户外 | 户外、旅行、生活技能、健康饮食 |
| 人文社科 | 历史、哲学、心理、经济、社会、**时政、社会批评** |
| 数字美术 | 绘画、插画、建模、动画、渲染；**以及设计** —— 平面/视觉/工业/UI/版式/配色/字体等设计原理与技巧。设计类内容归这里，**不另设「设计」夹**（用户 2026-10-07 确认） |
| 数码 | 硬件、外设、评测、选购 |
| **杂项** | 兜底。判不出来、或与任何专业领域无关的「有意思的小视频」都进这里 |

**「游戏开发」与「游戏相关」的分界线**（用户 2026-10-07 明确定义）：

> 游戏开发中只记录游戏开发技术和游戏设计相关的视频，对应程序、技术美术、策划这些相关内容。

所以：**讲怎么做一个游戏 → 游戏开发；讲一个游戏本身怎样 → 游戏相关**。做开发日志、发教程、拆架构、讲设计方法论的算前者；评测、评分、行业分析、求职面试、文化考据、实况攻略算后者。

「杂项」要保持**可被掏空**的性质 —— 它是兜底，不是主题。将来若其中某类内容凑够阈值独立成夹，那些条目就该被迁走。

技术类视频（计算机 / 游戏开发 / AI）另有 **21 个二级子类**，见 `bili_subs` 的既有口径 —— 只在给这三类写「二级子类」和「内容描述」时才需要，其余分类不需要二级子类。

## 判定口径

**输入**：标题、简介、UP 主是**主判据**；封面是**按需启用的复核手段**。不调接口、不读字幕（理由见 api-behavior.md）。

### 两遍判定：文本在先，封面按需

**第一遍 —— 只读文本**（标题 + 简介 + UP 主 + 历史结论），给出初判去向。默认**不看封面**。
读图是要花 token 的，"逐条都看" 是浪费：绝大多数条目的标题已经足够定性。

**第二遍 —— 只对「文本判不动」的条目看封面**。命中任一条件才升级：

| 触发条件 | 说明 |
|---|---|
| 标题是纯符号/编号，或简介为空 | 文本信息量确实不够 |
| 标题与简介互相矛盾 | 需要第三方证据裁决 |
| 初判落到兜底夹**「杂项」** | 杂项是最容易误收的地方，值得复核一次 |
| 初判卡在**细分类边界**上 | 游戏开发 vs 游戏相关、摄影 vs 数字美术、AI vs 计算机、游戏相关 vs 杂项 |
| 自评置信度 `low` | 已经承认判不准了 |

不命中以上任何一条的条目，**直接按文本判**，不要为了"严谨"去看图。

### 为什么不能反过来

**看图会制造错误。** 实证：`#72《为什么越简单的设计越高级？》` 标题已写明是设计原理、
历史结论也是「数字美术」，但重扫时看了封面（一张男装上身展示的截图）就改判成「生活户外」——
封面截帧与视频主题无关是常态（片头画面、口播镜头、广告位、UP 主自拍）。用户批注指出这次是封面误导。

对照正面例 `#120`：标题写「滑旱冰」，封面里并不是旱冰鞋 —— 那次看图确实救了场。
两者的差别在于：**封面的信息量有没有超过标题**。所以封面不是"比标题更权威的真相"，
它只是文本不足时的补充证据。

**允许用封面推翻文本的唯一条件**：封面与文本**明显冲突**，且封面内容能解释标题为什么这么写。
仅仅"封面看着像别的题材"**不足以**改判。

### 素材与成本

`judge_material.py` 会把封面裁成拼版接触表（contact sheet），一次看十几张。

- 第一遍：`--no-sheet` → 只出文本素材。
- 第二遍：把需要看图的 idx 收进 `judge/need_cover.json`，跑 `--sheet-idx` 只给这批出接触表
  （接受 idx 数组，也接受判定文件自动挑出 `low` 的）。
- 实测收益：606 条里只有 4 条需要看图时，接触表从 42 张降到 3 张。

**输出**：每条给三样 —— 去向、中文理由、置信度。

理由必须**具体到可复核**，写清是哪几个词或哪个主题让你这么判的：

- 好：`标题含「Spine 骨骼动画」，属 2D 骨骼动画工具链`
- 差：`看起来是游戏相关的`

**顺序**：
1. 命中历史结论的优先沿用（`history.json`），口径明显不对再改；
2. 命中下面「用户校准经验」的，**优先于任何关键词规则**；
3. 其余按主题判断。

**拿不准的尺度**：从严。只标真正判不出来的 —— 标题是纯符号、简介为空、或者内容横跨两三个领域且没有主次。**不要用 `low` 兜懒**，也不要为了「显得严谨」把明明很清楚的条目标成拿不准。参考比例约 10%。

判不出来时：

- **不要随便塞进某个主题夹**，塞进兜底夹；
- **不要为了分类而去抓更多信息**；
- 在理由里写明为什么拿不准（例如「标题只有编号，简介为空，无法判断主题」）。

## 兜底与新建夹

- 装不下的进「杂项」，**不擅自新建夹**。
- 例外一（skill 自己判断）：同类新内容**凑够 15 条**，才考虑新建一个主题夹。低于阈值仍进杂项，并在给用户的报告里点明「疑似新领域：X（N 条）」。
- 例外二（**用户直接下令**）：用户明确说「新增一个 XX 分类」时，**不再受 15 条阈值限制**，立即建夹 —— 但要触发全库重扫，见下节。
- 新建的夹名要短、要和现有夹名风格一致（两到四个汉字为主）。用户已指定的名称原样采用。

## 已在别的夹里怎么办

移动是「加入目标夹 + 从源夹移除」，**不会**抹掉视频原有的归属。所以会出现「一条视频同时属于多个夹」。

处理原则：**列出来给人决定，不自动清理。**

`plan_moves.py` 会把「视频已在别的夹、且本次去向与那个夹不同」的条目单独列进 `move_plan.md` 的「冲突」一节。这些条目的常见成因有两种：

1. 用户当初随手收的，确实该重判 → 人可能会想清理旧归属；
2. 视频真的横跨两个主题（一门课既讲渲染又讲架构）→ 保留多归属是对的。

工具区分不了这两种，所以不猜。

## 用户校准经验

**这一节会随使用增长。** 每次整理收尾时，把用户在本轮写下的「审阅批注」读回来，归纳成规则追加到这里。

### 交叉归属优先级链

当一个视频同时沾到多个技术领域时，按这条链归属（**前面的赢**）：

```
AI  >  游戏开发  >  计算机
```

依据：用户明确「AI 和游戏开发相交 → AI」（2026-10-07 #48）、「计算机和游戏开发相交 → 游戏开发」（2026-10-07 #208）。两句话合起来就唯一确定了这条链。

**AI 在链顶**：连「AI × 时政/社会批评」也让 AI 赢（用户 2026-10-07 确认）。例：#455《中文互联网的凋零，可能正杀死中国人工智能的未来》应留 AI，不因它是社会批评而改判人文社科。

### 冲突处理

规则之间撞上时，按顺序：

1. **AI 相关规则优先** —— 优先级链顶端，压过其余主题判断；
2. **时政/社会批评规则次之** —— 它们的作用是把内容从「杂项」抬升到「人文社科」，不是把内容从主题夹拽走；
3. **封面类规则不参与主题裁决** —— 它管的是"要不要看图"，不产出去向；
4. 其余按普通主题判断。

**不要**为了套规则而制造规则。若某条视频需要"解释一下才勉强能套上"，那就是没命中规则，按普通口径判。

### 沉淀的方法

读数据表的 `审阅批注` 字段（只取非空的），先**判断值不值得沉淀**，再决定怎么写：

| 类型 | 特征 | 处理 |
|---|---|---|
| **通用规则** | 能推广到没见过的条目（"带『考研』字样的数学课一律进数学"） | ✅ 进上表，优先级高于关键词规则 |
| **个例修正** | 只对这一条成立（"这条其实是讲 XX 的"） | ❌ 不成规则，只改这一条的去向 |
| **体系调整** | 涉及夹名、粒度、新增夹 | ⚠️ 单独立项改分类体系（见下节），不写进上表 |
| **判定质量反馈** | 指出系统性偏好（"你太爱把 XX 塞进杂项"） | ✅ 写成注意项进上表 |

门槛：**同一判断出现 2 次以上**才提炼成规则；只出现 1 次的先记为个例观察。模棱两可的一律按个例处理 —— 规则被单条特例污染，比少一条规则更糟。

写规则要用**可执行的条件**，不要写「注意质量」这种没有操作含义的话。

## 体系变更时怎么办

分类体系不是只增不减。用户提出**新增分类夹**（或改名、拆并）时：

0. **先做覆盖性检查 —— 别闷头建夹。** 用户说「新建 XX 夹」时，先核对现有夹的定义是否已经覆盖了它，
   并把重叠**明确说出来**再往下走。
   实证：用户 2026-10-07 批注「新建一个『设计』分类」，但既有「数字美术」的定义本就含设计 ——
   报明这层重叠后，用户改口「放入数字美术即可」，**省掉了一次全库重扫**。
   用户对分类体系的记忆不一定和当前体系一致；你的职责是把现状摆清楚，让他重新决定。
1. **不要只对新收集的视频生效** —— 用户 2026-10-07 明确要求：*「以后如果我提出新增分类的指令，你需要重新扫描完整的数据库，并将其中符合新分类的视频重新归类到这个新分类中。」*
2. 因此"新增夹"必然触发一次**全库重扫**（`rescan`，见 SKILL.md 阶段 2 的说明）：把数据表里**全部**记录（不只本轮待整理的）按新体系重判一遍。
3. 重扫还要顺带修正**新规则带来的历史误判** —— 例如新增优先级链后，原先因无链而误判的条目会被纠正。
4. 重扫结果仍然要过人工门禁：只把**去向发生变化**的条目摆给用户看，没变的不必占用注意力。
